# #11 4.0：动画资料与全站展示改善计划

日期：2026-10-13。状态：调研完成，改善方案待实施。本轮交付计划，不修改页面实现、业务数据或资源图片。

## 1. 目标与范围

4.0 的目标是让资料关系准确、页面层级清楚、相同功能在全站一致。完成程序检查不能替代资料核对和实际视觉验收。3.0 的完成记录保留为历史，不能作为这些新问题已经解决的证明。

验收范围按七类资料页面组织：动画、制作人员、创作者、角色、声优、歌曲、专辑。动画包含作品页和剧集子页。音乐操作、图片查看、吸顶导航涉及活动等其他页面时，覆盖相同功能的全部入口。

沿用本站已确认的蓝橙导航、白色资料表面、人物规范双色、搜索筛选与播放器语言。保留零构建 Vue、Node、Python 工作流，不引入整套 UI 框架，不增加数据库或通用图片代理项目。变化集中在资料关系、受影响的共享组件、图片资源和页面布局。

最新选图要求以用户本轮意见为准：动画目录使用统一规格的正式作品封面，取代此前混用横幅与原比例分享图的方向。

## 2. 已确认的问题与证据边界

调研基于本地 `9562e5ee15e94e42060aa525a1d13f2f033b18da`，分支 `ay-dev`；用户的 `.impeccable/config.json`、`uma_tools/trans_cache.json` 修改及已有未跟踪文件保留。

### 2.1 制作人员混杂：有展示错误，也有需要复核的数据关联

- 目录没有名为 OCT 或岐阜県地方競馬組合的剧集。两者出现在 `staff[].institutions`；相关条目共 90 条。这不能证明机构与每个人的关联都准确，但说明当前例子的“假剧集”首先来自展示语义错误。
- `uma_tools/app.js:874` 的 `groupAnimeParticipation` 把机构纳入岗位分组键。模板又把机构、版本、集数放进同一种标签容器。同一岗位遇到不同机构信息就拆行。
- 阿部憶人在芦毛灰姑娘的协力记录中，第 1–4、15 话没有机构字段，其余相关集数带岐阜県地方競馬組合。需要保留这个来源差异，同时在一个协力岗位下表达，不能简单删除机构或把全部集数归到该机构。
- 全量扫描发现 126 位人员的 137 个“人员—作品—段落—原岗位”组合有不止一种机构组合。这是需要检查的候选集合，不是已判定的 137 个数据错误。
- 原岗位有 279 种文本，展开后的岗位有 261 种。`app.js:715` 只固定了十个主要岗位的顺序，其余岗位并列后依赖来源出现顺序。
- `app.js:792` 按人数不超过六人决定默认展开，解释了用户看到的不一致。

### 2.2 封面与 Hero

- 浏览器复现：动画目录卡片同为 232px 宽，高度分别为 249、272、291px。`anime.css:5` 的 `align-self:start` 加上不同标题、说明行数导致卡片不齐。

### 2.3 简介、音乐、图片查看

- 新时代之门的中文简介确实把角色写成比萨胜驹。电影官网故事中的角色是ダンツフレーム，本站角色库 `dantsuflame` 的规范中文名是烈焰快驹。应复核原文后重写整句，而不是让模型凭名字猜改。[电影官网故事](https://movie-umamusume.jp/)
- 当前共有 11 段作品简介和 126 段剧集简介。本轮已检查作品简介及明确错误，尚未逐段确认全部剧集简介正确；全量人工语义复核属于实施阶段。
- 主模板的五处 `track-play` 与一处 `track-add` 分布不对称；动画、角色、声优关系中的 release 行只有播放。已有 `addSongTrack`、`addAlbumTrack` 和播放器入队逻辑可以复用，问题不是缺少队列能力。
- 动画音乐模板 `赛马娘LIVE相关.html:769`、角色和声优关系模板把歌曲再展开为发行专辑，造成专辑—歌曲—专辑重复与层层面板。
- `image-viewer.js:4` 捕获所有 `.entity-cover img`。浏览器验证制作人员生成 SVG 有放大光标，点击后确实打开查看器。
- 查看器在读取远端原图时隐藏当前图片；缺少缩略图保留、渐进替换、双指缩放与自然尺寸缩放策略。控件使用 Unicode 字符和独立硬编码样式。
- RTTT 一张本地剧照缩略图约 56KB，浏览器资源耗时约 54ms；原 PNG 为 1,775,492 字节，curl 样本总耗时 1.69s、首字节约 0.82s。浏览器打开查看器 2.5s 后仍未显示该原图。RTTT 剧场版封面仍直接取远端 JPEG，curl 样本约 0.86s。
- 上述是当前机器的单次样本，不是网络分位数，也不能据此单独归因 DNS、代理或服务器。跨域详细计时可能受 Timing-Allow-Origin 限制，不能把缺失或零值认作瞬时完成。[Resource Timing](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming)

## 3. audit 诊断

审计范围是本轮受影响的资料展示组件，评分是有限样本下的暂定判断，不是全站 WCAG 合规认证。

反模式判断：未通过。已见到歌曲与专辑重复嵌套、岗位逐个大面板、身份图中的微小文字与无意义装饰、资料页重复总数。目录的封面网格本身符合浏览作品的用途，不把所有网格一律视为错误。

- 可操作性与键盘：2/4。已有按钮标签、dialog、关闭恢复滚动；Hero 图片入口仍是不可直接键盘操作的 img，手机动作按钮约 40px 高。
- 性能：2/4。已有本地 WebP 和部分懒加载；远端原图阻塞显示、没有渐进预览，部分封面仍直连远端。
- 响应式：2/4。390px 样本无整页溢出；Hero 图片明显过小，操作层级弱，长标签和查看器工具栏需要专项检查。
- 设计 token 一致性：2/4。本站有可沿用的 token；查看器、姓名回退图、个人信息仍存在独立配色和尺寸。本站未要求新建暗色主题，不因缺少暗色模式扣分。
- 结构与反模式：1/4。重复发行层、逐岗位折叠、总数和装饰占用信息位置。

合计 9/20，属于需要结构改善的范围。确认的主要问题归为九项 P1：人员语义、简介错误、音乐层级、音乐动作遗漏、作品封面与卡片、Hero 层级、人员密度与排序、原图查看、个人信息布局。三项 P2：回退身份图不统一、总数及前作入口冗余、长页缺少持续可达的栏目导航。本轮没有确认页面完全不可用的 P0；不列无证据的 P3 清单。

保留的有效基础：规范实体 ID、原署名和机构字段，官方来源登记，本地缩略图，现有路由和播放器，已建立的共享搜索/筛选及人物双色。按 `/arrange` 重建层级，针对资源路径优化，再用 `/animate` 加交互反馈，最后 `/polish`；修复后重新 `/audit`。

## 4. 数据与参与关系改善（意见 1、10、14）

### 4.1 以关系语义组织数据

展示顺序为“作品 → 版本或内容段落 → 岗位/出演 → 机构上下文与具体剧集”。机构不能进入剧集集合，版本不能与其下的集数平铺为同一层级。

制作人员参与履历建议如下：

```text
芦毛灰姑娘
  协力
    第 1、2、3、4、15 话
    岐阜県地方競馬組合：第 5、6、7……话
```

一个岗位只出现一次；机构用带标签的次级文本，集数用可点击剧集链接。没有机构字段的记录不补写雇主，不推断永久所属。片头、片尾和正篇分别表达，不能因岗位相同合并掉内容范围。

全量核对人员和机构是否错误串联、复合岗位是否正确拆分、段落是否正确、是否重复、关联剧集是否属于当前作品；重点复核前述 137 个候选组合。使用已有证据定位原帧；只有真正影响身份或关系、无法自行闭环的疑项集中交给用户。保留此前确认的楊烈駿/楊烈瞬和鹿戸大介/鹿戸大輔独立身份，不重新开展整个历史 OCR 重跑项目。

### 4.2 全量简介复核

逐段检查作品与剧集简介：人物实体、剧情主体、事件和集数对应、原文含义、名称译法、版本差异、重复或空泛概括。先读取已存官方日文及来源，再修中文；维护现有名字映射，不能用自动同义词替换把别名变成另一角色。标题也要一并检查，不只查正文。

自动匹配用于发现候选，人工作语义核对。没有充分剧情来源时使用能确认的短概述；不编造补齐。修源数据后重新生成 catalog/index/API 产物，不能只改生成文件或翻译缓存。

### 4.3 RTTT 与人物出演

```text
ROAD TO THE TOP
  剧场版     [进入剧场版出演栏目]
  网络版
    [第 1 话] [第 2 话] [第 3 话] [第 4 话]
```

角色自己的出演页删除逐作品重复的本人角色名。声优页也去掉单角色时重复的角色行；同一声优在某作品配多个角色或非角色库角色时，保留必要的角色区分，放在作品范围内，不把它变成每个链接都重复的标题。必须保留剧场版证据及链接，网络版的集数只属于网络版。

同步覆盖角色、声优、制作人员、创作者、歌曲、专辑中的动画关联入口。浏览器回退、直达 URL、Ctrl/Command 点击、栏目与 edition 参数都要保持正确。

## 5. 作品封面、剧集图与 Hero（意见 5、6、7、8、9）

### 5.1 作品目录封面

目录采用统一 2:3 的作品封面槽与对齐的标题、元信息区。优先选正式竖版主视觉的无发行日期版本，整幅作品主体清晰；不用 OGP、倒计时、上映日期广告、店铺宣传和普通剧照充当默认封面。

逐作品查正式素材，先追官方网站及发布记录。umamusu.wiki 的图库可作为查找线索，确认图的类别与出处后选择，不能按搜索命中就批量替换。若某短篇没有正式竖版图，采用该作品的正式主视觉在统一槽中完整呈现；必要时克制留白，不生成假海报，不强裁关键人物、标题或广告日期以假装另一版本。只有无法找到适合素材时才列出明确例外交用户判断。

所有卡片等高且同一行对齐；短标题也保留一致标题区，多行长标题保持可读，不靠随机固定整卡像素高度或静默截断来遮掩内容。

### 5.2 区分图片用途

沿现有数据和素材清单补最少必要字段，表达作品封面、剧集缩略图、图库图、原图和来源。电影海报与剧集缩略图不共用选图逻辑。已有 `url/original` 继续兼容；图片种类应按用途区分，不按 SVG/PNG 扩展名决定真假。

剧集缩略图采用 16:9：先选官方该话关键剧照，其次官方该话视频缩略图，再考虑可追溯的该话画面。检索和归属必须准确到集。为 126 个剧集逐个建立选图结果，优先处理目前没有任何剧照的五组作品。找不到该话素材时明确回退到作品封面，界面不能将作品图标成该话独有画面；不把“回退有图”当作缺图工作已完成。

已找到合适素材的页面必须补齐，不再把过去缺图范围直接判为接受。真正无可取得素材的剩余项集中说明，不伪造画面。

### 5.3 Hero 重构

作品 Hero 在桌面以约 220–280px 的竖版封面与正文双栏构成；图片实际尺寸随页面宽度调整，不能被蓝橙装饰区挤成图标。剧集 Hero 使用较大的 16:9 画面区，作品封面作为缺少剧集图时的明确回退。

内容分四层：作品/剧集身份与标题；公开时间等事实；简洁简介；操作。手机按图片与标题、事实、简介、操作自然重排，不保留一条高大的装饰色块和一个几十像素的小图。

播放平台属于观看动作；官方网站属于资料外链；全部剧集、上一话和下一话属于站内导航；RTTT 的版本切换属于内容范围。四者分区，权重不同。观看入口优先，剧集导航单独一行，官方网站保持次级。没有下一话时不生成伪按钮；多个平台不挤成与导航混在一起的胶囊墙。

合并等价日期，保留真正不同的放送、上线和发行时间，不机械显示同日两遍。不展示前作/衍生自信息或按钮；底层有来源的关系数据保留，避免破坏其他消费者。

## 6. 制作人员名单（意见 12）

### 6.1 推荐：紧凑岗位表，默认完整展开

桌面为左侧岗位、右侧人员的可换行资料行；机构是该岗位中的次级上下文。单人岗位一行表达，不用整宽深浅色标题条、人数、折叠箭头和下一行姓名。按制作环节用小标题与细分隔组织，不逐岗位做面板；手机岗位在上、姓名自然换行，保持同一阅读结构。

全部岗位默认显示，不按人数改变。主要制作、片头、片尾等内容范围有明确分区；搜索保持岗位和机构上下文，不让搜索结果再次变成大量折叠控件。初版不使用只渲染可见行的虚拟列表，避免干扰页内查找和完整复制。

备选方案为“按制作环节的大分区折叠”，但所有分区默认展开，用户显式收起才改变；不再按人数阈值决定。其优势是极长原画/背景名单可以整体收起，代价是部分人员仍需展开才能查阅。优先采用紧凑完整表，实际浏览仍过长时再选择大分区折叠。

### 6.2 全量固定岗位顺序

建立一份共享岗位展示顺序，覆盖当前 261 个展开岗位：原作与企划 → 导演与剧本 → 分镜与演出 → 角色/道具/动作设计 → 作画与动画 → 美术 → 色彩与上色 → CG/3D/二维制作 → 摄影与特效 → 剪辑与后期 → 音乐/音响 → 制作管理与制片 → 宣传/发行/授权 → 协力与特别鸣谢。

上述是拟定分区，实施时依据现有规范岗位逐项落位；不把岗位名强制改成分区名。复合岗位先按已有 roles 展开，人物在一个岗位中的重复署名去重但保留原始证据。片头、片尾范围下复用同一顺序。未知新岗位采用明确可重复的次级排序并纳入维护，不回到来源顺序。

## 7. 原图查看器与图库（意见 3、13及补充）

### 7.1 开源方案研究结论

- PhotoSwipe v5：推荐作为本次落地候选。纯 JS、无需新构建系统、MIT；提供缩放、触摸、响应式图像和可定制 UI。[官网](https://photoswipe.com/)
- PhotoSwipe v6：官方正在讨论将 ZoomView、PageView、Dialog 与 UI 分离，是值得参考的前沿方向。当前官方仓库仍介绍 v5，并把 v6 标为开发计划，不能按已正式发布的稳定 API 写本次实施承诺。[官方 v6 计划](https://github.com/dimsemenov/PhotoSwipe/discussions/2170)
- lightGallery 3：官方已有 headless 内核、手势、缩略导航、响应式加载和窗口化等能力，适合更大、更复杂的图库；本次可参考其界面与核心分离、工具栏溢出策略，不为几百张资料图自建渲染层。[headless 文档](https://www.lightgalleryjs.com/docs/headless/)
- lightGallery 的许可证是 GPLv3，或使用商业许可；是否适合本仓库需核对已有许可条件，不能因为可下载就当作 MIT。[许可说明](https://www.lightgalleryjs.com/docs/license/)
- Viewer.js：MIT，触摸、键盘、缩放、旋转、翻转能力齐全；偏图片工具箱，可作为需要图像检查操作时的备选，本次不需要完整旋转/翻转工具。[官方仓库](https://github.com/fengyuanchen/viewerjs)
- GLightbox：MIT，纯 JS，图片/视频/iframe 混合弹层方便；本次需求主要是图片阅读，优先比较缩放和渐进加载体验。[官方仓库](https://github.com/biati-digital/glightbox)

这些是文档与接口调研，不等于已在本站完成候选库集成验证。实施时只选一个，使用本地静态资源和很薄的本站适配层，保留许可；不同时加载多库或换前端框架。

### 7.2 查看器的统一体验

页面只给明确可查看的真实封面、照片、剧照、图库图片建立入口。原创身份 SVG、占位图、失败回退图、普通界面图标没有“查看原图”和放大光标。入口是语义化链接或按钮；即使 JS 失败，真实原图链接仍能使用。

打开先显示已加载缩略图，随后清晰图替换；持续等待时有不遮图的进度反馈。工具栏分为关闭、上一/下一、适应窗口/原始尺寸、打开原图；使用本站同一 SVG 图标、按钮圆角、字号、hover/focus 状态。窄屏保留关闭和关键缩放，次级操作收进明确菜单，不换行压掉画面。

深蓝中性的遮罩衬托图片，颜色、层级、控件从本站 token 派生；不把蓝橙大渐变铺到图片后面。单图隐藏上一/下一；可提示当前图序，不在动画页面增加图库总数。

支持拖拽、边界约束、焦点位置缩放、双击/双指缩放、键盘、Esc、关闭后焦点和滚动恢复。按实际原图大小计算适应窗口和 100%，不把固定五倍 CSS 缩放当作原始尺寸。[缩放文档](https://photoswipe.com/adjusting-zoom-level/)

统一的一处主要动效为“缩略图展开到图片阅读层并在关闭时返回”：打开约 240–300ms、关闭约 180–220ms；图片不在当前视口、尺寸缺失或过大时改淡入。减少动态偏好关闭空间位移；不随意给 Hero、列表每一项增加入场动画。[过渡文档](https://photoswipe.com/opening-or-closing-transition/)

原图动作和来源信息通过库的 UI 扩展口接入，不复制手势引擎。[UI 扩展](https://photoswipe.com/adding-ui-elements/)

### 7.3 性能方案

首轮实施测冷缓存、暖缓存、缩略图、首次大图、连续切图与手机网络，分别记录请求、下载体积、解码和首张可见时间；浏览器与 curl 样本分开记录。

已有本地 WebP 用于目录和首次预览；为确认可保留的原始素材与大图沿现有素材维护流程建立同源版本，远端原图作为来源链接和备用。不是新增通用代理服务。保留完整原件，不从低清缩略图插值生成“高清原图”。

目录、Hero、查看器采用不同清晰度；首屏 Hero 优先加载，屏外图库懒加载。点击后优先当前图，邻图预取有界，手机不预取整个画廊。注意 PhotoSwipe 的内置邻图预载有最低行为，应实测而不是假定 `preload:[0,0]` 就不会请求邻图。[加载与预取配置](https://photoswipe.com/options/)

原图下载失败仍保留预览，给重试和来源链接；不显示成“没有图片”。原图地址使用显式来源字段，不通用删除 URL 的全部查询参数。缓存采用现有资源版本策略，保证更新后可见，不新增 hash gate。

### 7.4 umamusu.wiki 的可借鉴点

用户已明确：该站不是优秀原图查看器标杆，而是全站图库资源参考。爱丽速子图库区分故事画面、动画视觉、社交插图、商品、游戏资产等；动画区还能区分关键视觉、发行视觉、封面和赠品。这对防止本站把广告图、封面与剧照混用很有帮助。[参考图库](https://umamusu.wiki/Agnes_Tachyon/Gallery)

源码可见缩略图和 2x srcset、原图尺寸信息及 MediaViewer 线索。借鉴“类型分区＋逐图说明＋缩略/原图分离”，不是照搬该站外观。本轮没有确认萌娘百科当前具体查看模块：页面读取受到限制，不能声称它已经验证使用某个库。

本次仅将相关图库用作作品选图、剧集图补齐和已有图片栏目组织的线索；全站角色数千张图库导入是额外内容项目，不默认加入 #11 4.0。第三方文件的文字许可不等于原始图片统一授权，选用时保留逐图出处并优先追溯官方资产。

## 8. 音乐层级与全站动作（意见 11）

动画音乐栏目以歌曲/实际录音为主要浏览对象，发行专辑作独立参考链接或紧凑发行信息。默认显示曲名、动画用途、适用版本/集数和右侧播放/加入；仅在同曲有多个真实录音时展开一次，录音行带发行信息。专辑可以单独出现为原声专辑入口，但不再展开成歌曲后又展开成同一专辑。

全站共享一对媒体动作：播放/暂停、加入播放列表。右侧位置、图标、尺寸、播放中与入队反馈一致；桌面同列对齐，手机标题可以换行但动作不能挤出视口，也不能夹进标题中。动作点击不能误触展开、路由跳转或封面。

覆盖歌曲目录/详情/录音与发行、专辑曲目、创作者参与歌曲、角色歌曲、声优歌曲、动画及剧集音乐、活动歌单和其他实际可播资源入口。复用现有播放器与录音标识，不维护多套入队函数。

有音频的录音必须出现两个动作；只有元数据而没有可播放录音的条目保持明确“暂无音源”，不能制作空播放按钮或错误连到另一版本。多录音条目根据明确选择播放和入队，不静默选不同唱段；歌曲页、播放列表和专辑页的录音定位一致。

## 9. 制作人员与创作者回退图（意见 2）

真实人物照片优先，来源明确的本人自画像可保留；缺照片者使用同一回退组件。方案均不采用两字圆圈、不混搭职业小图标、不在小头像中塞条码和全文微字，不让回退图进入原图查看。

### A. 排印字章（推荐）

方形白纸底，深蓝的大字形作为中心，克制的蓝橙角标呼应本站。中文/日文以一个有辨识度的姓氏字为主，拉丁姓名以大写首字母处理；重点是字形、留白和方章结构，姓名全文在头像外的真实文本中显示。44px 与 Hero 大图都使用同一构成，32px 不依赖细线。优点是资料馆语言一致、能迅速读到姓名线索；缺点是同姓不能靠头像唯一识别，仍以姓名为准。

### B. 几何织纹

正方形内由两三块宽色面、负形和斜切构成，使用本站蓝色族与少量橙色。人物固定使用一个构成，制作与音乐领域不改变骨架。没有人物文字或职业图标。优点是小尺寸清晰、可以避免千人同头像；缺点是抽象纹样不承担姓名识别，需要控制变化数量，不能声称每个人都有独一无二的官方标识。

### C. 中性人物剪影

少量简洁的头肩形状与纸面背景，固定线重和轻微色差，不生成假真人、动漫脸或职业服装。优点是立即表达“人物”，对长姓名和拉丁姓名友好；缺点是容易同质化，风格控制不好会像通用通讯录。

暂定推荐 A，B 适合用户希望彻底去掉姓名字形时，C 最克制。最终视觉选择保留给用户，不把推荐写成已经通过的设计。实施时先用中日文、长拉丁名、同姓人物在目录和 Hero 中比较，再全量替换。

## 10. 个人信息与总数（意见 4、15）

角色、声优个人信息统一为资料清单：同一白色表面，桌面两列字段，标签用稳定列宽与次级文字，数值自然对齐，长事务所/别名可跨列；手机一列。用行间距和细分隔表达关系，不在几个字后垫一小块灰底，不用嵌套卡片或零值统计填空。

姓名、生日、出身地、事务所、角色设定等各按现有可信字段排列；原型马和声优关系继续是明确可点击链接。无资料时沿用适合该字段的未知状态，不制造内容。人物 Hero 使用已有规范双色，信息区以可读白纸为主。

动画、制作人员及创作者页面删除所有汇总数量展示：目录结果数、参与作品/剧集数量、岗位人数/机构数、Hero 集数总数、关系标题统计、分页的记录总数等。按本轮“任何地方不体现总数”的字面执行，不自行保留“11部”“共13话”等例外。当前集数序号、片长、日期、目录中的具体剧集链接仍是内容事实。

内部数量字段可以继续用于生成与排序，不污染前台。角色/声优信息区中作为填充的歌曲和出演统计也移除，具体歌曲与出演放在对应栏目中查阅。

## 11. 长页导航与搜索筛选（意见 12）

科学名称是 sticky contextual header / condensed header（吸顶上下文栏/收缩页头）、sticky tab navigation（吸顶栏目导航）、sticky filter toolbar（吸顶搜索筛选栏）。这是滚动中的持续导航能力，不是再造一个完整 Hero。

建议采用：原 Hero 离开视口后，同一条上下文栏显示小封面/姓名、当前栏目和栏目切换。桌面在现有全站导航下方一条完成；手机仅显示短身份与横向栏目，图片可省略。返回 Hero 区时恢复原始结构，触发稳定，不随每一小次上下滚动反复闪现。[MediaWiki 吸顶页头研究](https://www.mediawiki.org/wiki/Reading/Web/Desktop_Improvements/Features/Sticky_Header)

七类详情及同类活动页复用这一能力，只有实际多栏目或长内容页面才启用。目录搜索与排序吸顶，完整筛选不全部强行常驻：手机用筛选按钮、已选条件和可展开面板，桌面按可用高度决定保留一行。详情与目录的交互不同，但偏移和层级规则一致。

实施用 CSS sticky 和原 Hero 边界观察，不每帧重算整个页面；核对祖先 overflow、全站导航高度、弹出菜单、查看器 top layer、底部播放器与手机安全区。菜单不被裁切，焦点/跳转位置不被吸顶遮挡，页面回退恢复位置，切栏目不会跳到错误的旧滚动高度。不能只写一个 `top:0`。[MDN sticky 定位](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/position)

目标是在长人员/歌曲栏目底部可以直接切换栏目；在长目录下修改搜索无需回顶。短页不增加无作用的固定条。

## 12. 实施顺序与完成标准

### 阶段一：资料关系与简介

修机构/岗位/集数/版本的语义混排，全量检查候选机构组合及关系；逐段复核 11 段作品与 126 段剧集简介，使用规范角色名。完成 RTTT 层级和人物重复名处理。此阶段以数据准确与所有使用者同步为验收，不以换色结束。

### 阶段二：图片素材与目录/Hero

逐作品选统一用途的正式封面，逐剧集落实缩略图及来源。修卡片等高、作品与剧集 Hero、按钮分组、移除前作/衍生与所有总数。验收素材本身，而不只验收图片请求成功。

### 阶段三：音乐与名单结构

取消音乐的发行循环嵌套，全站统一播放/入队；完整岗位顺序、紧凑名单、统一默认状态；角色/声优个人信息重构。确定回退图方案后统一制作人员与创作者头像。

### 阶段四：原图查看、性能与长页导航

采用一个成熟查看器，本站按钮/遮罩/动效适配；真实图片明确授权入口；渐进加载与同源资源策略；详情和目录吸顶。前面完成素材与布局后再做缩略图展开动效，避免动画适配错误素材和未稳定位置。

### 阶段五：七类页面及全站同类验收

在 1440px、1024px、390px 和窄屏样本下实际浏览，不只检查 DOM 存在。覆盖长标题、复合岗位、大名单、多机构、多录音、无音源、无照片、缺图、加载失败、RTTT 两版本、OVA/蓝光短篇和连载剧集。图片手势需触摸设备或明确说明模拟测试的限制。

核心验收场景：

1. 阿部憶人履历中 OCT/岐阜机构不能像剧集按钮，同一协力岗位不重复拆标题，机构所属集数正确。
2. 角色自己的动画出演不重复本人名称，声优多角色不丢信息；RTTT 的网络版集数位于网络版下面，剧场版入口有效。
3. 作品卡片对齐、正确正式封面；剧集显示该话图；每个真实剩余素材缺口有明确原因。
4. 手机 Hero 有清晰图片与标题层级，平台/资料/导航操作分开，无水平溢出。
5. 音乐不循环嵌套；每个实际可播录音右侧有播放与加入；两个动作不触发展开或错录音。
6. 岗位顺序在作品、单集、人员履历中一致；默认状态一致；姓名/机构可检索，全部内容可访问。
7. 原创 SVG 与失败占位图不能打开查看器；真实图片可打开，慢网有预览，缩放/切图/关闭/回退正确。
8. 动画/制作人员/创作者所有栏目无汇总总数和前作/衍生入口；个人信息没有局部灰标签拼贴。
9. 长页能直接切栏目或修改搜索，吸顶栏、菜单、播放器和查看器不遮挡。

运行受影响生成器、现有关键测试、实际页面/API；新增测试仅覆盖有意义的关系和行为回归，不为每条 CSS 写镜像测试。最后 `/polish` 检查字号、行距、图标、状态、边距、动效和全站一致性，并重跑受影响行为及 `/audit`。

按资料、素材/Hero、音乐、名单/信息、查看器、吸顶等清晰关注点组织小提交。每阶段记录实际完成项与剩余问题，未核对的资料不宣称通过。只提交本任务文件，保留用户工作；用户明确表示批次可以提交 PR 后，再按约定执行最终 rebase、全批次验证与推送。本计划不创建或更新 PR。

## 14. 设计样稿与沟通细节

用户认可整体计划后，提供 [SVG 与原图查看器样稿](design/pr11-v4/index.html)。样稿使用本地 PhotoSwipe 5.4.4（MIT，许可随文件保留），不是正式页面接入；三张 1920×1080 官方原图为对应来源的完整本地副本。样稿的 A/B/C 切换只改变预览，不自动提交用户选择。

回退图并列展示制作人员、音乐创作者和拉丁姓名，提供 44px 与详情尺寸。查看器桌面提供上一/下一、缩小/放大、适应窗口、100%、打开原图、关闭；手机保留缩放、更多、关闭，其余操作在更多菜单。失败演示保留预览并支持重试。正式接入还需手机实机手势和全站入口验收，不把样稿通过当作生产接入完成。

旧 3.1 OCR 台没有待处理候选，按用户授权退役。精简结论保留 17 组历史校正/归并与 2 组用户决定及其原帧；删除 172 组近似姓名的详细候选包和不支持实际处置的采样帧。源转录、原署名、规范实体、正式来源登记以及用户历史截图保留。4.0 的机构、岗位、简介核验继续；出现真实新疑项时，提交问题、当前值、原始证据与推荐处理，不复活整个旧候选台。

需要选择和说明的细节：

- 回退图选择 A/B/C；A 同姓、B 几何相似、C 中性剪影都可能相同，不能让头像承担唯一身份识别。头像外的全文姓名与规范 ID 仍是身份依据。
- 无竖版正式作品图时，推荐让正式主视觉在统一槽中完整显示。若用户更愿意把画面裁成竖版封面，需要先比较具体素材，不能自动裁掉标题或人物。
- 无官方剧集图时，推荐先查官方视频缩略图；仍缺失时明确回退到作品图。公开第三方图库画面作为线索，是否将其作为最终展示素材需就具体来源决定。
- 当前“任何地方不体现总数”包括 Hero 的集数总数和岗位人数。日期、片长和当前集数序号保留。若用户只想去掉汇总统计而保留作品的集数事实，可以缩窄这个范围。
