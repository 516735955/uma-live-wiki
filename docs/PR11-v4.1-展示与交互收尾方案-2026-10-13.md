# #11 4.1 展示与交互收尾方案

日期：2026-10-13。状态：调研与方案完成，查看器外观及 Hero 活动范围已确认，尚未实施。调研基于 `cc43a7364ffe8e6a004eef50d17973bbedadfe58` 的本地页面与源代码。

## 1. 目标与范围

4.1 修复关系内容被推到右侧、悬停破坏按钮、音乐操作越界、合唱者被过滤和活动返回失效等问题，使 4.0 已建立的数据与关系真正以一致、紧凑、可连续浏览的方式呈现。

用户的九项意见全部纳入：制作人员履历、搜索筛选硬填充、原图查看器重写、原子页面按钮状态、音乐动画关联、活动关联与返回、机构识别、人物动画出演、播放与添加及完整演唱阵容。七类资料页面仍是验收主体：动画、制作人员、创作者、角色、声优、歌曲、专辑；共享组件的活动、旧现场歌单、其他资料目录入口同步检查。

沿用本站蓝橙导航、纹理背景、白色资料表面和人物规范双色。保留 A 排印字章、已补齐的作品与剧集图、来源记录、固定岗位顺序、默认展开的紧凑人员名单，以及作品—版本—剧集的语义。此次不重跑历史 OCR、不恢复已退役审阅台，不重新选择 SVG 方向，不引入 UI 框架或另一套路由系统。真正无法确认的资料关系集中沟通，其余按来源自行闭环。

## 2. 已复现的根因

调研使用正常动效的桌面浏览器，主要视口为 1440×1000，另检查 390×844。以下是当前实现的实测，不是修复后的验收结果。

### 2.1 同一布局错误影响四类关联展示

`anime-participation` 同时用于制作人员履历、创作者动画履历、角色／声优出演、歌曲／专辑动画关联。`uma_tools/anime.css` 中 `.anime-participation-work .credit-ledger` 把所有后代列表指定到网格第二列、第二行；4.0 模板把列表放入 `.participation-edition-group` 后，该定位仍然生效，于是内层生成不需要的隐式列。

- 山本健页的一个版本分组左边为 x=199，岗位列表却从 x=708 开始，空出约 509px。
- 名将怒涛第一季出演分组左边同为 x=199，单个“第 6 话”列表从 x=727 开始。
- 该版本分组的计算列宽为约 524px、584px；这些列没有表达任何真实的信息层级。
- 无需角色名或集数的剧场版仍渲染空 `dl`，占用空网格轨道。

这解释了意见 1、5、8 的主要现象。修正应收回网格定位的作用范围，建立明确内容区，不能靠缩小整页宽度或给每个页面分别加负边距遮盖。[CSS Grid 自动定位与隐式轨道](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Grid_layout/Auto-placement)

### 2.2 搜索栏的白色是共享吸顶样式造成的

`context-navigation.css` 对目录直接子级 `.archive-toolbar` 和 `.archive-filter-row` 无条件设置 `background:var(--card,#fff)`，未区分原位与吸顶状态。实测动画、制作人员、创作者、角色、声优、歌曲、专辑七类目录，以及活动目录，工具栏背景均为纯白。创作者工具栏在页面顶部、尚未滚动时已经呈现白色矩形。

此次 CSS 检索得到的白色声明不能一律当作错误：输入框、专辑卡片、资料阅读表面本就需要自己的背景。需要修的是无语义的整条填充和覆盖，不是把全站白色改成透明。

### 2.3 原图控件确实会重新排版

查看器依赖 PhotoSwipe 5.4.4。其原生 `.pswp__button:hover/:active/:focus` 会设置 `padding:0`，本站文字按钮的静态规则只用单类选择器设置左右 12px，优先级不足。

- “适应窗口”：hover 前 88px，hover 后 64px。
- “100%”：约 65px → 41px。
- “打开原图”：约 109px → 85px。
- 三者均缩窄 24px，顶部其他内容随之移动。键盘 focus 也命中同一原生规则，不能只补 hover。

现有适配还包含独立深色工具栏、重复的 z-index 声明、末尾 `font:inherit` 覆盖文字字号、底部操作说明和隐藏的加载指示。这次重写本站查看器的外观、控件与状态适配，不继续叠零散覆盖。PhotoSwipe 官方提供实例作用域、图标变量和 UI 扩展接口，足以保留成熟手势底层并实现本站自己的完整外观。[样式定制](https://photoswipe.com/styling/)、[UI 扩展接口](https://photoswipe.com/adding-ui-elements/)

### 2.4 剧集按钮混用了两个状态体系

`anime.css` 把剧集导航 `.horse-link-chip` 的背景固定为 `--ui-soft`；`app.css` 的通用 `.horse-link-chip:hover` 将文字改成白色并加橙色阴影，却不能覆盖更具体的浅色背景规则。

摇曳马娘第 3 话的“第 4 话”按钮实测 hover 为白字 `rgb(255,255,255)`、背景 `rgb(245,247,252)`，对比约 1.07:1，解释了截图中的文字消失。这个错误不能通过只修改文字颜色、但继续保留相互冲突的按钮语义解决。

### 2.5 活动关联与历史记录各有错误

当前动画源数据只有一条 `target_type:event` 关系，即新时代之门完成披露首映。活动目录已有其他明确与动画有关的上映、舞台问候和专题节目，尚未关联。

反向关联 `.anime-crosslink-grid` 即使只有一个条目，也固定使用两列。实测容器宽 1170px，唯一链接宽 579px；箭头位于半宽链接末端，因此看起来居中。

电影页点击完成披露活动时，历史记录实际为：

```text
电影页
  push 活动基础地址
  push 活动默认场次地址
点击返回
  回到活动基础地址
  路由恢复再次 push 默认场次地址
  又停在活动页
```

`openEvent()` 在路由恢复期间也调用 `pushUrl()`，默认场次规范化被错误地当成一次用户导航。`navigateTo()` 的 `fromEntity` 还依据目标地址判断，活动场次地址与部分原子地址的识别范围需要一并核对。既要避免重复历史，也要正确记录来源。

### 2.6 两个按钮塞进了一个按钮的列

`.relation-release` 桌面操作列仍是 38px，手机也保留 38px；新 `EntityActions` 为 36px×2、间距 8px，实际需要 80px。

和多田美咲歌曲页展开英文版 Umapyoi Legend：桌面行右边界 x=1282，操作组右边界约 x=1324，越界约 42px；390px 视口中行右边界 x=347、操作组右边界 x=389，同样越界。手机旧规则还只给单个 `.track-play` 指定跨行位置，新操作组未获得对应布局。

全站仍有三种活跃的资源操作实现：`EntityActions`、专辑 `.track-play/.track-add`、活动和旧现场 HTML 的 `.setlist-track-actions`。当前 hover 分别有变蓝放大、收缩、变橙上移；活动播放按钮没有共用组件的暂停图标状态。旧 `.music-card-play` 等规则是否可删，需先确认模板、运行时生成 HTML 和源歌单引用，不能只凭主模板检索删除。

### 2.7 合唱数据完整，展示函数只保留当前人物

`relationReleaseVocalists()` 使用 `filter()` 只返回当前角色或声优，角色、声优歌曲栏共用这一函数。`song-umapyoi-legend-e1d012a94c` 的英文录音原数据有 10 位演唱者，页面只显示和多田美咲；这不是需要重新 OCR 或补歌手的数据缺口。

### 2.8 机构被样式抹成了不明确的普通文字

人员名单中机构沿用 `.credit-role-tag` 元素，但后续样式去掉边框和背景，变成约 12.8px、灰色、850 字重的文本。角色、岗位标签和机构使用相近元素却缺少可见语义。芦毛灰姑娘第 13 话可复现 ROLL2、CygamesPictures 等实例；机构应在对应名单内获得适度、明确的识别。

## 3. 关系列表重排（意见 1、5、8）

### 3.1 统一结构，按内容自然长高

外层只负责封面、正文和导航箭头；正文内部按作品标题、版本、岗位或用途、具体剧集排列。只对直接子级使用外层网格位置，内层采用正常的单列流和局部岗位列。删除没有实际内容的空列表。

桌面封面约 56–64px 宽，正文紧随其后，标题和详情左边缘一致。箭头固定在标题行最右侧，长标题自然换行并为箭头预留槽位。行与行之间采用轻分隔与 16–24px 间距；版本与内容间约 8px、岗位行约 6–8px。没有大面积彩色块、逐岗位卡片或人为统一的高行。

制作人员的呈现结构：

```text
[封面] ROAD TO THE TOP                                     →
       剧场版
         导演
         分镜
         动画演出
       网络版
         导演                 [第 4 话]
         分镜                 [第 2 话]
         舞台动画 · 分镜      [第 4 话]
```

这只是布局示意，实际岗位与剧集始终来自当前已核对的数据，不据示意补写履历。岗位标签采用稳定、有限宽度，过长的完整岗位允许换行；剧集标签紧挨所属岗位，不能漂到半页以外。机构差异保留在岗位内部的对应集数范围，一个协力岗位不会再次拆成两个主标题。

### 3.2 角色和声优出演

本人单角色出演不重复写本人名字，也不保留空岗位占位。普通电视作品标题下直接排列剧集；RTTT 的剧场版和网络版分组紧凑，电影版链接本身表示出演范围，网络版的剧集只出现在其下面。

声优确实为多个角色配音时，保留必要的角色范围标签。不能为了统一外观删去区别多个角色所需的信息。单话、无集数电影、长集数、同作品多角色、多个版本都作为实际验收样本。

### 3.3 歌曲和专辑关联

专辑关联以“作品标题 → 原声专辑等关系用途”紧邻呈现，不再把用途放到右端。歌曲关联以“作品 → 版本 → 使用方式与录音版本 → 对应剧集”排列；“插入曲 · TV Size / 13 话 Ver.”允许在自己的用途列换行，集数仍位于该行内容区。

只有一个短用途的行保持紧凑；集数多的行自然换行，不将文字和集数摆在页面两端。保持歌曲—版本—录音关系，不重新制造专辑—歌曲—专辑嵌套。

改动集中在 `app.js` 注册的 `anime-participation` 和 `anime.css`，七类调用点共同受益；仅在必要的实体语义上使用已有参数，不复制六份独立模板。

## 4. 搜索、筛选和吸顶表面（意见 2）

目录搜索／筛选在原位时，外部容器恢复与纹理背景连续的表面，不加白色整条底板和底部阴影；输入框、下拉和筛选胶囊保留各自有意义的阅读与操作表面。

进入吸顶状态后，使用与本站页面一致的淡色背景及低强度纹理、细分隔线，保证滚过来的内容不会穿过输入框和文字。原位与吸顶只改变表面，不改变高度、padding 或占位；不采用透明文字叠在滚动内容上的做法，也不使用全屏背景模糊。

在现有吸顶逻辑内识别是否越过工具栏原始位置，更新有限状态；切换页面时移除旧观察，不新增全站管理框架。手机筛选展开时，两层吸顶高度仍由实际工具栏尺寸决定；内容区域内滚动，页面底部不能被永久遮住。

排查范围包含七类目录、活动目录、详情内搜索、关系图／其他资料目录的同类筛选和浮动导航。逐一判断硬填充的用途。资料表、Hero、专辑封面卡片应保留白色阅读表面，不能被统一透明规则误伤。

完成标准：页面顶部、吸顶后、手机筛选展开、滚回顶部四种状态无突兀白条、无闪烁、无尺寸变化；背景连续且文字可读。

## 5. 原图查看器重写（意见 3）

### 5.1 成品外观

已确认采用白色工具栏与海军蓝蒙版，接近本站资料面板。保留 PhotoSwipe 的缩放、拖动、手势和切图底层，重写本站适配层及控件样式。工具栏使用白色阅读表面、海军蓝文字和图标、品牌蓝操作边界及少量橙色反馈；画面区使用本站海军蓝的遮罩。工具栏和画面区有明确分工。

桌面约 64px 高的顶部栏：

```text
图片标题                         [−] [+] [适应窗口] [100%] [打开原图 ↗] [×]

                        原图／渐进预览画面
              [上一张]                         [下一张]
```

只有实际多图图库显示左右切换与简短的当前序号；单图不出现无意义的切图按钮。标题在现有槽位内截断，不挤压操作。没有底部说明、双指操作提示、快捷键提示或新增说明小字。

手机顶部保留标题、缩小、放大、更多、关闭；“更多”容纳适应窗口、100%、打开原图。关闭始终在固定槽位可见。操作菜单使用同一白色表面和蓝色文字，点击外部、Esc 或执行操作后关闭，打开时不会推动画面和顶部按钮。

### 5.2 按钮行为和状态

- 缩小／放大：在允许范围内调整缩放；到边界后禁用对应按钮，图标仍可辨认。
- 适应窗口：完整显示图片，在画面区居中；小图默认不强制放大到模糊。
- 100%：按原图像素尺寸显示；使用真实原图尺寸，不能拿缩略图尺寸当原图尺寸。
- 打开原图：新标签访问真实原图，不关闭当前查看器，不把来源页面混称原图。
- 上一张／下一张：只在当前图库内切换，不串到其他作品。
- 关闭：恢复原滚动位置、入口焦点与页面操作；不影响播放状态。

所有控件固定高度、内边距、边框厚度和字重；文字按钮预留确定宽度或稳定槽位。默认、hover、focus、active、disabled 都在专用实例作用域内完整定义，覆盖 PhotoSwipe 原生状态规则。hover 只改色和轻反馈，按钮与相邻元素的边界不能移动。图标沿用本站线条规格，禁止 Unicode 字符临时代替图标。

工具栏位于画面上方，加载状态用操作栏里的小型进度图形表达。保留即时缩略预览，原图载入后在原位置替换；失败显示正常字号的简短错误状态、重试和打开来源，不用底部小字说明承担错误反馈。

### 5.3 蒙版、动效和入口

打开时从真实图片的可见边界过渡到画面区，约 220–260ms；关闭约 180–220ms。被裁切的缩略图必须正确映射裁切范围，无法可靠映射时用淡入，不能用不准确的 zoom 造成拉伸。遮罩与画面使用 opacity／transform，工具栏按钮不做会移动相邻控件的缩放。[PhotoSwipe 开闭与裁切缩略图规则](https://photoswipe.com/opening-or-closing-transition/)

遮罩复用本站海军蓝和库的 `bgOpacity`；不叠加全屏 blur。官方明确提示全屏背景模糊会影响性能。[PhotoSwipe 背景定制](https://photoswipe.com/styling/)

正常动效和 reduced-motion 分开验收。图片入口只覆盖真实封面、肖像和图库图；A 排印字章、占位图和原创身份 SVG 不显示放大光标、不注册查看入口。打开另一页、快速关开、图片失败和横竖屏改变不能留下锁滚动或浮层。Wikimedia MediaViewer 可借鉴图片浏览与原始文件入口的分工，但不引入其庞大的文件元信息界面。[Wikimedia 查看器文档](https://doc.wikimedia.org/MultimediaViewer/master/js/js/)

改动为 `image-viewer.js`、`image-viewer.css` 及必要的图片入口属性。保留原版 vendor 文件，避免修改库源码制造升级负担。

## 6. 全站按钮状态一致性（意见 4）

明确三种按钮用途：站内导航、外部观看／来源、音乐资源操作。剧集导航不再借用原型马链接的完整 hover 规则；仍可共享基础尺寸和图标，但各用途独立定义背景与文字的成对状态。

站内导航默认浅蓝灰底、深蓝字；hover 用更明确的浅蓝或蓝边界，文字保持深色。主观看按钮默认品牌蓝、白字，hover 使用深品牌蓝、白字。次级外链默认白底蓝字，hover 浅蓝底蓝字。所有状态保持原有尺寸与稳定图标位置，不只改其中一个颜色。

全站检查 Hero 外链、上下集、全部剧集、版本切换、关系链接、返回、筛选、分页、重试、图片查看和音乐操作。人物链接保留对应人物色，但同时检查颜色对文字的影响。

验收逐项经过默认、hover、focus、active、disabled；尤其检查白色文字是否对应真正的深色背景。可见文字不可依赖阴影来“勉强能看见”。重点修复已证实的状态冲突，不开展无关主题改造。

### 7.2 数据与双向表示

动画关系继续维护在 `data/anime/relations.json` 和既有来源登记中，由现有生成器产出 catalog／relation index；新增活动使用 `data/events/README.md` 指定的可维护源层和现有合并方式。优先匹配已有 ID、场次、地点和时间，避免另造重复活动。不能直接手改生成 catalog，不能改写人工维护的现场歌单 HTML。

同一条关系表达作品或剧集、版本、活动与必要场次范围。反向由同一条关系生成，不能双向各写一套不同数据。实际只上映前两话的关系必须保留单元范围；RTTT 剧场版上映不可挂到网络版单集。原子页面的关系标题不能出现虚假的剧集或机构。

### 7.3 Hero 内的关联活动

动画 Hero 内按“身份 → 事实 → 简介 → 观看／外链 → 相关活动 → 剧集导航”的用途分区。相关活动用紧凑行，展示关系类型、活动标题、实际日期与末端箭头；不再放在 Hero 下方独立的大橙边胶囊里。关系类型保持正常可读字号，属于必要事实标签。

多个活动按先行／完成披露、初日／首映、后续上映／舞台见面会、作品专题分组，各组按日期排序。内容过多时 Hero 先呈现最直接的上映类，提供“展开相关活动”显示其余已确认范围内的关系，不显示作品总数，也不把十几项挤成胶囊墙。手机一行内容自然换行，箭头有固定末端槽位。

剧集页优先显示精确关联该话的活动；一般作品活动若展示，明确属于作品级，不能让用户误以为该话被上映。

### 7.4 活动页面的反向关系

现有反向板块改为紧凑的全宽内容行：封面、作品标题、关系类型、必要版本／剧集、最右箭头。一个条目不占半个网格。多个条目也按资料行排列，不为凑两列制造空白卡片。

关系箭头的末端槽位与上述参与列表共用布局原则，检查其他同类关系行。只让图标自身产生微小位移，标题和整个行不能随 hover 跳动。

## 8. 页面返回与浏览连续性（意见 6）

以现有 History API 和路由恢复逻辑修复，不建立并行的页面栈。

- 一次明确的页面跳转只新增一次历史记录。
- 自动选默认场次、旧地址规范化、路由恢复使用替换或只读恢复，不新增历史。`popstate` 期间不能再次 push 当前默认场次。[History.replaceState](https://developer.mozilla.org/en-US/docs/Web/API/History/replaceState)
- 上下文返回依据真实的内部来源，正确识别活动场次和剧集等原子地址；直接打开／刷新不制造虚假的返回入口。
- 栏目、edition、version、release、session 和列表筛选必须跟随对应 URL 和已有状态恢复。保留来源页滚动位置，不能只回到作品默认首页。
- 浏览器返回、前进与页面返回使用一致的历史；不采用“连退两次”的临时补丁。
- 切页、返回、进入图片查看器不会清空队列或重复播放。异步旧请求不得覆盖当前页。
- 普通链接仍支持 Cmd／Ctrl 点击、新标签和复制地址。

必须实走：动画／剧集 → 活动场次 → 返回；活动 → 动画／剧集 → 返回；歌曲／专辑 ↔ 动画；制作人员／创作者 ↔ 动画；角色／声优 → 歌曲／活动 → 返回；多步链路的连续返回与前进。至少一例从带栏目、版本参数且已滚动的位置出发。

## 9. 机构名称适度突出（意见 7）

岗位列、机构分组、人员名字保持现有紧凑排列，岗位全开和固定顺序不变。

机构在对应分组的起点显示明确的“机构：”前缀；机构本身是该岗位署名主体时，不再重复一个没有意义的前缀。采用约 14px 的正常资料字号、500–600 字重、清楚的蓝灰文字，可用极浅底色与轻边界作局部分组标识。人员名字仍是主要链接，机构不使用主操作蓝橙填充，也不在每个人后面重复机构。

手机机构置于所属名单上方，长名称完整换行；多个机构保留来源中的顺序。机构字段只表达当前署名上下文，不自动称“所属公司”“雇主”，不制造机构详情链接或根据缺字段推断归属。协力机构与人名保持语义区分，不能再次变成剧集标签。

这些是数据标签，不是解释性小字；不新增“本页面如何使用”或“OCR 说明”等辅助文案。

## 10. 统一播放和添加，完整显示演唱阵容（意见 9）

### 10.1 一套资源动作

所有音乐资源行、录音行、专辑曲目、动画音乐、活动曲目和旧现场歌单，使用同一套播放／暂停与加入行为及外观。优先复用 `EntityActions`；运行时生成的旧 HTML 使用与组件一致的按钮结构和事件适配，保护原始歌单内容与排序。

播放默认品牌橙、白图标；hover 深橙、白图标。添加默认白色或透明阅读表面、蓝色边界与加号；hover 浅蓝、深蓝加号。播放中显示暂停图标且同步实际播放器状态，不能某页只有变色、某页仍显示播放。hover 保持按钮尺寸，active 只有图标或局部按压反馈，不放大整个操作组。

播放当前曲目执行暂停／继续；选择另一录音按现有规则立即播放。添加只入队，不跳页、不展开父级、不切换当前播放。短暂在原按钮内显示成功反馈，不能靠追加小字或加宽文本让行抖动。重复加入沿用现有队列策略，不擅自改成禁用所有已加入资源。

无音频的记录不显示假播放按钮；有来源外链的记录保持来源语义，不能把 Spotify／视频外链伪装成本站可直接播放的录音。专辑整体播放／加入保留批量含义，外观用同一动作家族。底部播放器的上一首、音量、播放列表等属于播放控制，可保留自身布局，不把它们硬套成每个资源旁的双按钮。

### 10.2 操作组获得真实空间

桌面录音行改为“发行信息弹性列、阵容弹性列、操作组自动宽度列”，两个文本列均允许缩小并换行。操作列至少容纳完整双按钮和间距，不沿用 38px。手机发行信息占第一行，第二行阵容与末端操作区自然排布，必要时阵容独占一行；按钮始终在所属记录内部。

普通紧凑资源行按钮可沿用 36px 视觉尺寸；触屏需要约 44px 的实际点击空间并在布局内预留，不能用重叠的透明点击区域补尺寸。专辑表格、旧现场表格与卡片操作也检查内部边界，不通过 `overflow:hidden` 裁掉越界按钮。

音乐卡片若继续使用角落操作，正文先预留真实操作区域；标题、演唱者和元信息不得被按钮盖住。更适合内容流的条目把操作放进正常布局，不为全站所有资源强行统一成绝对定位。

### 10.3 当前人物优先，其余完整保留

当前角色／声优上下文只影响顺序，不改变演唱阵容。将原数组稳定分为当前人物匹配项和其他项，两组内部保留原始顺序，再合并。返回新数组，不原地改变 catalog，也不从作品级集合推断具体录音的歌手。

英文版 Umapyoi Legend 在和多田美咲或名将怒涛页面的预期声优顺序：

```text
和多田美咲 → 前田玲奈 → 高桥未奈美 → 佐伯伊织 → 夏吉优子
           → 伊藤彩沙 → 佐藤日向 → 下地紫野 → 野口百合 → 秋奈
```

显示名使用本站规范名字映射；上面顺序取自该录音的原始 `vocalists`，不是姓名排序。其余页面无当前人物上下文时保持原顺序。同一声优确有多个角色记录时，使用能区别录音／角色的稳定 key，避免 Vue 使用单一声优 ID 漏渲染；只有数据本身完全重复才按既有规则去重。

这首 10 人合唱完整换行显示，不默认折叠成一人，也不通过省略号隐藏另外九人。检查角色和声优歌曲栏、歌曲版本、专辑曲目、动画录音、创作者录音及播放器元信息是否仍有类似过滤。当前人物优先规则用于人物上下文，不污染全局歌单和播放器的规范阵容。

## 11. 有限审计与额外收尾

受影响组件的有限审计：可操作性 2/4、性能 2/4、响应式 2/4、设计 token 一致性 2/4、结构与反模式 2/4，合计 10/20。依据是已复现的低对比状态、hover 改宽、手机操作越界、独立查看器样式和无意义隐式列；这是本轮组件诊断，不能与 4.0 的不同样本评分直接比较，也不是全站认证。不因本站没有暗色主题扣分。

P1 包括活动历史循环、按钮不可读、动作越界、合唱者遗漏、关系列严重错位与查看器状态抖动。P2 包括目录硬底色、活动关联缺口、机构语义弱和单条关系半宽；没有确认 P0，不追加无证据的 P3 清单。

- 清理受影响组件的互相覆盖规则和确实不再使用的空 DOM；修改原规则，不在文件末尾无限叠更强选择器。旧歌单仍引用的类先兼容，再判断是否移除。

### 11.1 临时文件与存储空间

## 12. 实施顺序与提交组织

2. **修复共享关系结构。** 一次修正 `anime-participation`、单条反向关联、空列表及末端箭头，同步七类调用点；保留版本／范围语义。独立布局提交。
3. **重写查看器适配。** 固定按钮状态、本站外观、渐进预览、菜单与动效；桌面和手机分别真实操作。独立查看器提交。
4. **完成表面与名单细节。** 目录原位／吸顶状态、机构分组和剩余共享动作入口；实际排查引用后清理冗余样式。独立 UI 提交。
5. **补齐活动数据。** 按十一部作品核对既有记录和官方来源，修源层、生成双向关系，把入口放到 Hero。将数据维护与关系展示按实际范围分开提交。
6. **整体收尾。** 正常动效下走七类页面和跨页链路，修复发现的问题，更新实际设计规范和完成记录。全批次验收后停止在 PR 之前，是否推送／提交 PR 仍由用户决定。

以上按风险和依赖排序，资料查证可穿插进行。实施中的真实疑项集中给用户，普通 CSS、列表顺序和已有证据的活动关系不需要再次确认。

## 13. 验收方式与完成条件

### 13.1 九项意见逐一有结果

- 意见 1：制作人员普通作品、RTTT 多版本、多岗位和片头／舞台动画范围都在标题下连续阅读，岗位不再漂到右侧。
- 意见 2：七类目录及同类入口在原位、吸顶、手机展开筛选、滚回原位均无突兀白条。
- 意见 3：查看器完整外观统一；所有按钮经过 hover／focus／active 后位置、宽度和相邻布局不变；底部说明删除；菜单、切图、100%、关闭、慢图、失败与重试都能操作。
- 意见 4：导航、观看和次级外链所有状态文字可读，没有白字落在浅底的组合。
- 意见 5：歌曲、专辑动画关联用途紧邻标题，长用途与集数自然换行，没有空列。
- 意见 6：已发现的活动候选闭环；新增关系来自证据；Hero 入口和活动反向列表语义一致；各返回链路恢复原 URL、栏目、版本及位置，不再循环。
- 意见 7：机构可辨认且不抢过岗位／人名，不被误解为永久雇主或剧集。
- 意见 8：角色和声优出演紧凑，单话、电影和多版本正确；必要的多角色范围保留。
- 意见 9：全部音乐资源入口动作样式与行为一致，操作组未越过所属内容边界，当前人物优先且合唱阵容完整。

### 13.2 浏览器验收补足 4.0 的缺口
